# code-essence

分析代码库，找出其核心抽象（最本质的那个循环/机制），输出结构化报告说明什么是核心、什么是外围。

## 核心理念

每个代码库都有一个**核心抽象**——一个根本性的机制或循环，所有其他功能都是围绕它展开的。理解这个核心让你能：

- 快速掌握项目本质，而不是迷失在细节里
- 在修改代码时有清晰的决策依据（它是影响核心还是外围？）
- 在面对一个陌生项目时快速建立心智模型

这个 skill 的使命就是：**把代码的表象剥开，找到那个让一切运转起来的东西，然后清晰地告诉你。**

## 触发条件

用户在以下场景中应该触发此 skill：

- **直接询问本质**："这个代码的本质是什么"、"这个项目的核心架构是什么"、"解释一下这个项目的核心设计"
- **请求分析代码库**："分析一下这个项目"、"帮我理解这个代码库"、"做一个代码审查"
- **面对陌生项目**：用户把一个项目交给你分析、修改或扩展，而你没有上下文
- **中文触发词**："本质"、"核心抽象"、"这个项目到底是什么"、"代码的骨架"
- **修改/重构前**：在你要对一个不熟悉的项目做修改或重构前，先理解其本质

> 原则：当你面对一个你没有完全理解的代码库，并且需要做出分析、修改或设计决策时，先运行这个 skill。

## 分析流程

你不应该直接输出报告，而是先**探索代码仓库**，获取足够信息后再得出结论。

### 第一步：探索仓库结构

动笔之前先动手翻。使用内置工具（`ls`/`find`/`grep`/`read`）主动探索：

```
1. ls -la 项目根目录，了解整体布局
2. 找入口：main.go / main.ts / index.js / src/main.py / package.json 的 "main" 等
3. 找配置文件：package.json / Cargo.toml / go.mod / pyproject.toml 等（判断语言和技术栈）
4. 读 README.md 了解项目定位
5. 看 src/ 或核心目录下的模块结构
```

**读文件，不要只看目录名。** 目录树只能告诉你有什么文件，不能告诉你这些文件在做什么。

### 第二步：深入阅读核心文件

**必须读文件内容，不要停留在文件列表。** 尝试用 grep 辅助定位关键代码：

1. **读入口文件** — 了解程序从哪启动，调用了哪些核心模块
   ```bash
   # 找到入口文件后，读取其内容
   read path/to/entry-file
   ```

2. **顺藤摸瓜** — 从入口的关键 import/函数调用出发，追踪到核心模块
   ```bash
   # 入口文件引用了哪些核心模块？依次读一下
   read path/to/core-module-1
   read path/to/core-module-2
   ```

3. **用 grep 辅助定位高频引用** — 哪个模块被整个项目大量引用？那通常是核心
   ```bash
   grep -r "from 'core'" src/ --include="*.ts" | head -20
   grep -r "import.*core" src/ --include="*.rs" | head -20
   grep -r "use.*core" src/ --include="*.go" | head -20
   ```

4. **读核心数据结构的定义** — 类型/接口/结构体定义揭示了设计的心智模型
   ```bash
   # 找到核心类型定义所在的文件并阅读
   read path/to/types-file
   ```

5. **读 README 和技术文档** — 作者通常会在文档中说明项目理念

### 第三步：定位核心抽象

基于你读到的代码，判断核心抽象属于哪种模式：

| 类型 | 示例 |
|------|------|
| **事件循环 / 主循环** | game loop, event loop, request-dispatch cycle, agent loop |
| **数据处理管道** | stream processing, ETL pipeline, message queue consumer |
| **状态机 / 状态变迁** | 有限状态机、工作流引擎、生命周期管理 |
| **插件/扩展系统** | 围绕一个扩展点设计的框架，核心抽象是"如何注册和调用插件" |
| **领域模型** | 一组核心数据结构及其不变量的约束系统 |
| **请求-响应循环** | web 框架的 middleware chain, HTTP handler dispatch |
| **编译/解释管道** | parser → AST → optimizer → codegen 的流水线 |

**判断标准**：如果你能删掉某个模块后整个项目就不能运转了，那就是核心。如果能删掉某个模块但核心功能仍然完好，那就是外围。

**不要猜测，用读到的代码说话。** 你的核心抽象判断必须基于你实际读过的代码内容。

### 第四步：输出报告

将报告直接打印到对话框。报告格式见下方。

## 分析策略（按项目规模）

| 规模 | 策略 |
|------|------|
| **单文件/小函数** | 直接读取全文 → 语义分析 → 输出报告 |
| **中小项目（<50 文件）** | 结构扫描 → 读取关键文件（入口、核心类型定义、核心模块）→ 语义分析 |
| **大项目（50+ 文件）** | 结构扫描 → 筛选候选核心模块 → 深入读取候选模块 → 语义判断 |

**大项目的候选筛选指标：**
- 被其他模块高频 import 的类型/函数
- 位于入口点核心调用链上
- 包含了项目中最核心的数据结构定义
- README 中重点描述、文档反复提及的模块

## 报告格式

必须严格使用以下模板。报告应该**精炼**，不要超过你能直接输出并让用户一目了然的长度。

```markdown
# code-essence: <项目名>

一句话总结——<项目名> 的本质是 <最核心的抽象>

## 核心抽象

<详细说明最本质的那个机制/循环，解释它如何驱动所有外围功能>

**为什么这是核心：** <说明判断依据——比如"没有这个循环，其他模块没有任何意义"或"所有模块最终都调用到这个抽象">

## 外围层

<按与核心的依赖远近排列各个外围模块>

| 层次 | 模块/组件 | 与核心的关系 |
|------|-----------|-------------|
| 核心 | <模块名> | 核心抽象所在的模块 |
| 直接依赖 | <模块名> | 被核心直接调用，或直接扩展核心功能的模块 |
| 间接依赖 | <模块名> | 建立在直接依赖之上的高层功能 |
| 基础设施 | <模块名> | 工具函数、配置管理、日志等支撑性组件 |

## 依赖方向

<数据流/控制流的主要走向。说明核心如何驱动外围，或外围如何回馈核心。>

例："agent 循环从终端读取输入 → 调用 LLM → 决定使用哪个工具 → 执行工具 → 将结果返回给 agent 循环做下一轮决策"

## 扩展点

<可扩展机制、插件接口、抽象层、设计模式。说明这个项目如何设计来支持变化。>

| 扩展点 | 机制 | 示例 |
|--------|------|------|
| <扩展点名> | interface/trait/abstract class/注册机制 | 具体实现例子 |

## 技术栈

<语言、框架、关键依赖、构建工具。只列出对理解项目重要的。>
```

## 重要原则

### 1. 精炼至上

不要写长篇大论。好的本质分析应该像电梯演讲——在几句话内让人建立心智模型。**如果用户需要翻页才能看完，说明你不够精炼。**

- 核心抽象写 1-2 段话，不要超过 200 字
- 外围层表格是核心，文字说明是辅助
- 技术栈只列出关键项（3-5 个），不要拉清单

### 2. 分层思考

每一层只需要知道它的下层是什么。不要在讲核心抽象时深入外围模块的实现细节，也不要在讲外围层时回到核心抽象的细节。

### 3. 客观归因

核心抽象的判断要有依据，不是猜测。在报告中说明"为什么这是核心"。

### 4. 承认不确定性

如果分析时间不足（项目太大、文件太多），明确说明分析的范围和局限性：

> "注意：我只扫描了 src/core/ 和 src/api/ 目录，src/vendor/ 目录（约 200 个文件）未包含在内。核心抽象可能在这些未扫描的目录中有扩展。"

## 示例

分析 pi（假设场景）：

```
# code-essence: pi

一句话总结——pi 的本质是 **agent 循环**：一个持续运行的回环，在"接收输入 → 调用 LLM → 选择工具 → 执行工具 → 收集结果 → 下一轮"之间循环。

## 核心抽象

pi 的核心是一个 **agent 循环（Agent Loop）**。这不是一个显式的 `while(true)`，而是一个递归的决策-执行-观察周期：
1. 收集输入（来自终端、文件、工具结果）
2. 构造提示词并调用 LLM
3. LLM 返回一个决策（输出文本、调用工具、或终止）
4. 如果是工具调用，执行工具并收集结果
5. 将结果作为新的输入，回到步骤 2

**为什么这是核心：** 没有 agent 循环，pi 只是一个静态的文本生成器。所有其他组件——模型供应商、终端 UI、插件系统、文件操作——都是为这个循环服务的。

## 外围层

| 层次 | 模块 | 与核心的关系 |
|------|------|-------------|
| 核心 | agent loop | 本质本身 |
| 直接依赖 | model provider / LLM 调用 | agent 循环的核心依赖，负责生成决策 |
| 直接依赖 | tool system | 被 agent 循环调用执行具体操作 |
| 间接依赖 | terminal/UI | 收集用户输入给 agent 循环，展示循环输出 |
| 间接依赖 | plugin system | 扩展 agent 循环的能力 |
| 基础设施 | config/file system | 被各模块引用但不参与核心逻辑 |

## 依赖方向

agent 循环是驱动者：
终端输入 → agent 循环 → LLM → 决策 → tool system → 工具结果 → agent 循环（下一轮）→ ... → 最终输出到终端

## 扩展点

| 扩展点 | 机制 | 示例 |
|--------|------|------|
| 模型供应商 | provider interface | OpenAI、Anthropic、DeepSeek 等 |
| 工具系统 | tool registration | read、bash、edit、自定义扩展 |
| 插件 | 标准插件 API | 自定义提示词、自定义工具 |
| 终端 | 抽象 IO 层 | TUI、Web UI、headless 模式 |

## 技术栈

- TypeScript — 主要语言
- Node.js — 运行环境
- 多模型供应商（OpenAI、Anthropic 等）
```

## 成功标准

分析完成后，用户应该能：
1. 用一句话说清楚这个项目是干什么的（核心抽象）
2. 知道哪些部分是骨架、哪些是血肉（分层）
3. 知道如果想改某个功能应该动哪一层（依赖方向）
4. 知道项目在哪些方向上是可扩展的（扩展点）

如果用户看完报告后还有"所以这个项目到底是什么"的疑问，那就是分析不够精炼或核心没抓准。
